# ADR 0025：資料庫往返次數（通知頁慢 13 秒的根因）

日期：2026-11-14。狀態：程式已寫並測試；**部署後要實測**。

## 現象
管理員開「站內通知」要等 13 秒以上，按「核准」要等約 10 秒。

## 根因（用 Worker 觀測紀錄確認，不是猜的）
- 業主在台灣（中華電信），請求被 Cloudflare 送到**洛杉磯（LAX）機房**，Worker 就在那裡執行；資料庫 D1 在**新加坡（APAC）**。Worker 與資料庫之間每次查詢要橫跨太平洋，實測每次約 0.18 秒（資料庫本身只要 0.4 毫秒）。
- 程式在迴圈裡「一位會員查一次」：審核紀錄每一列查 5～6 次，所以 12 列約 60 次排隊 ≈ 11～13 秒（觀測：`/v1/admin/reviews/history` 牆鐘 10～13.6 秒、CPU 只有 20～77 毫秒）。
- 每個後台請求光驗證身分就連查 3 次（登入、職務、額外權限）≈ 0.55 秒；通知頁前端又是 `me → reviews → history` 一關接一關。
- 按核准後整頁重新載入一次，且按鈕沒鎖住（紀錄裡有連按造成的 404）。

## 修正
1. **Smart Placement**（`wrangler.jsonc`）：讓 Worker 搬到資料庫旁邊，請求只橫跨一次太平洋，不再每個查詢一次。免費。
2. **一次查多位會員**（`src/db/member-bulk.ts`，一個 `db.batch` ＝ 一次往返）：審核清單、審核紀錄、會員查詢清單都改用它；往返次數不再隨資料列數增加。
3. **驗證身分一次往返**（`staffContextByToken`）；頁面路由同一請求只查一次登入（`currentSession` 快取）。
4. 核准流程中互不相干的查詢改為同時送出。
5. 前端（`notes.ts`）：通知清單先出現、審核面板另外補上；`reviews`、`history`、欄位標籤三個請求同時送出；按核准／駁回立刻鎖住按鈕、顯示「處理中…」、畫面上先移除該筆，之後只更新審核紀錄與通知，不再整頁重載。
6. 防退步測試 `test/roundtrips.test.ts`：資料變多時往返次數必須不變（且 ≤ 6）。

## 規則（之後寫程式要守）
- **不可在迴圈裡 `await` 查資料庫。** 列表一律先收集 id，再用 `memberBriefs` 或 `IN (...)` 一次查（D1 單一語句最多 100 個參數，已分批）。
- 互相獨立的查詢用 `Promise.all` 或 `db.batch`。
- 新增的列表型 API 要加進 `test/roundtrips.test.ts`。

## 尚未處理（記錄）
- 後台「詞庫」重新命名／合併等管理操作仍有迴圈查詢（少用、資料量小）；若變慢再比照處理。
- D1 讀取副本（read replication）可再降低讀取延遲，但要改成帶書籤的寫法，目前不做。
