# ADR 0032：會員資料批次查詢（100 筆）與上手欄位

日期：2026-11-20　狀態：採用（杜杜龍同意，行動大學課程報名名單需求）

## 背景
行動大學的課程「報名名單」要顯示學員的上手白金、上手鑽石（Amway 資料，行動大學不得保存），要一次查一整頁（以及匯出時分批）。

## 現況與決定
- 欄位本來就存在：`upline_platinum`、`upline_diamond`（Amway 專區，文字、`review: never` 沒有待審核狀態、不是會員 ID）。`POST /v1/apps/{app_id}/members/lookup` 本來就能查（杜杜龍在「平台設定」勾選才回傳，沒勾 403 `field_not_allowed`），不需要新增欄位或改回傳形狀。
- **上限由 50 改成 100**（`MEMBER_LOOKUP_MAX`）；超過回 422。
- **效能**：`lookupMemberData` 原本每位會員查 2～4 次資料庫（違反 ADR 0025，100 位約 200 次、依 0.18 秒一次估計超過半分鐘）。改成一次 `db.batch` 查一整批（會員、個人欄位、會員編號、Amway 欄位），D1 單一語句最多 100 個參數，所以依欄位數分成約 95 個一組；100 位約 2 次往返加 1 次稽核。`test/roundtrips.test.ts` 防退步。
- **順序**：`members` 依請求順序（同一個 id 一次）；查不到的（沒在該 App 登入、已停用、已刪除）在 `not_found`，不讓整批失敗。**維持 `{members, not_found}` 形狀**（不是「每個位置一個 null」），因為那會是 `/v1` 的破壞性變更；App 用 `not_found` 對應即可。
- **頻率**：每個 App 每分鐘 120 次（沿用 `RL_READ` 綁定，以 `svc-members:<app_id>` 為鍵；超過 429、`retry-after: 60`）。
- **稽核**：沿用 `members.lookup`（App、筆數、回傳筆數、欄位名稱、用途；不記內容）。
- 隱私不變：只回杜杜龍勾選的欄位，沒有信箱、電話、會員編號（除非勾選 `member_number`）。

## 後果
- 平台規範：串接指令包（三、11 新增一條；檢查清單 30）與 `docs/integration-guide.md` 6.9，升版 `2026-11-20.2`；順便修正上一版檢查清單兩條都編成 29 的編號。
- 不新增資料表、不需 migration。
